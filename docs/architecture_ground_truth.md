# Architecture Ground Truth

**Date Confirmed:** 2026-07-09

The production model (`cricket_stance_advanced_v4.keras` and `v2.keras`) is a `[Conv1D(64) -> BiLSTM(64) -> TemporalAttention -> Dense(32) -> Dense(4, sigmoid)]` network with **76,395 trainable parameters**. This architecture has been definitively confirmed via `model.summary()` on the actual deployed `.keras` artifacts.

Crucially, this **perfectly matches** the current `academic_scripts/train_advanced_model.py` script. The training script and the deployed artifacts are completely in sync.

The previous claim in the SRS that the "BiLSTM was abandoned" was incorrect. The model is currently and actively using a Bidirectional LSTM wrapper with 64 units (resulting in an output shape of 128).

**Update, 2026-07-18 (Milestone 1 — ML single-source-of-truth consolidation):** `TemporalAttention` was previously defined independently in four places (`train_advanced_model.py`, `backend/backend/api/ml_service.py`, `dataset/inference_service.py`, `academic_scripts/eval_uncertainty_correlation.py`), with no guarantee any two stayed in sync. It is now defined once, in `dataset/model_layers.py`, and every consumer imports it from there. The feature schema (`SEQ_LEN`, the 30-feature list) is similarly now sourced from `dataset/schema.py` everywhere it's used by production-serving code (`ml_service.py`, `inference_service.py`) and by the training script itself (`train_advanced_model.py`). `inference_service.py`'s prior copy used a different Keras API surface (`tf.keras.backend.dot`/`softmax`/`sum` vs. `tf.tensordot`/`tf.keras.activations.softmax`/`tf.reduce_sum`) than the other three copies — verified numerically identical (max absolute difference `0.0` on a random test tensor) before consolidating onto the single canonical implementation, and the consolidated model's deterministic (dropout-disabled) forward pass was confirmed byte-for-byte identical to the pre-consolidation output on a real video. The architecture and parameter counts documented below are unchanged by this consolidation — it relocated code, it did not alter the model.

**Update, 2026-07-18 (Milestone 3 — Stance-Symmetry-Aware Temporal Confidence):** `kinematic_validator.py`'s bone-length CV filter (`kinematic_valid`, a boolean) is no longer the only quality gate on training data. `dataset/academic_scripts/stance_symmetry_confidence.py` adds a second, complementary, mandatory filter per the frozen V2 spec (Section 6.2): a continuous per-frame `temporal_confidence` score in (0, 1], combining (a) cross-frame trajectory-smoothness — a normalized second-difference/jerk of each of the same 12 joints `kinematic_validator.py` already tracks, scaled by that joint's own path length so genuine swing motion isn't penalized — and (b) a stance-phase symmetry prior — bilateral hip/knee/ankle angle differences at the stance/trigger phases only, z-scored against a reference distribution fit empirically from the real dataset (n=613 stance/trigger frames across the then-798-session `keypoints_validated.csv`: knee mean=0.14°/std=20.10°, hip mean=-0.91°/std=24.15°, ankle mean=-1.78°/std=18.71°). `merge.py` now drops frames below `MIN_TEMPORAL_CONFIDENCE` (0.5, empirically set to flag ~2.9% of real frames) the same way it already drops `kinematic_valid == False` frames, but — unlike `kinematic_valid` — keeps the continuous score in `dataset.csv` rather than discarding it after gating, since Milestone 5 (Confidence-Gated Attention, not yet implemented) is expected to consume the continuous score at inference time. Real run against the production dataset: of 2,938 frames that already passed `kinematic_valid`, 82 (2.8%) scored below `MIN_TEMPORAL_CONFIDENCE` and a further 359 (12.2%) scored NaN and were also dropped (see below) — 441 of 2,938 frames (15.0%) total, affecting sessions across the dataset. Because `feature_engineering.py`'s existing session padding (`reindex` to the 7 canonical phases + `ffill`/`bfill`) fills in for a session's dropped frames from its remaining ones, the filter's cost to final training-ready sequence *count* is smaller than its raw-frame impact — this is a pre-existing characteristic of the padding logic, not something this milestone changed, and is flagged here because it affects how "yield cost" should be read.

**Review fix (2026-07-18, Principal Engineer pass):** the initial implementation used post-sort row *position* as a proxy for phase index (position 0 = stance, position 1 = trigger, ...). Verified against the live dataset, 42 real sessions have every `frame_name` duplicated (e.g. two `"01_stance"` rows before the first `"02_trigger"` row) — for those sessions, position 1 was actually a second copy of the stance frame, not the real trigger frame, silently corrupting both the symmetry prior (comparing the wrong phase) and the jerk calculation (an artificial zero-then-jump pattern from the duplicate pairs, not real motion). Fixed: `compute_session_confidence` now detects a duplicate `frame_name` within a session and returns NaN confidence for that entire session rather than a number that looks valid but isn't — merge.py's gate drops NaN the same way it drops a sub-threshold score. Separately, `TRAJECTORY_JOINTS` was a hand-retyped copy of `kinematic_validator.py`'s `BONES` endpoints (a real drift risk); it is now derived directly from `BONES` by import. Both fixes are covered by new regression tests in `test_stance_symmetry_confidence.py`.

**Second review fix (2026-07-18):** the ablation's significance test was checked against what it actually compares, not just whether it ran without error. Its first implementation called `make_folds` independently for each variant (filter on, filter off) and then paired their per-fold MAEs by position (fold 1 vs. fold 1, etc.). Verified directly against the real dataset that this was invalid: fold 1 of the unfiltered variant held out `{devduttpadikkal, farrangeytdatset1, youtubedataset22, ...}` while fold 1 of the filtered variant held out an almost entirely different set, `{josbuttler2, shikharDhawan, youtubedataset36, ...}` — a paired test requires the same held-out subjects under two conditions, and these weren't. The test still silently returned a p-value (0.3125, then 0.4375 across two runs) despite the pairing being meaningless. Fixed: folds are now built once from the unfiltered variant's identities, and the SAME held-out identity set is reused to evaluate the filtered variant every fold (a fold is dropped from both sides if the filter removed all of that fold's held-out identities' sessions). The index arithmetic doing this (`derive_paired_split`) was extracted into its own pure, TensorFlow-free function specifically so it could be unit-tested in isolation — it had zero test coverage when the bug above was found, despite being exactly the kind of subtle indexing logic that class of bug lives in. Covered now by 5 tests in `test_ablation_stance_symmetry_filter.py`, including a regression test reproducing the original bug's shape.

The required ablation (`ablation_stance_symmetry_filter.py`, run against the full real dataset, 5-fold identity-grouped CV, Conv1D+BiLSTM+Attention — the same architecture as the deployed model), **re-run after both review fixes above**: at the current labeled-data scale (120 complete 7-frame sequences, 10 unique identities without the filter — the bottleneck is label coverage, not this filter), the new filter costs 6 sessions of yield (120 -> 114, 1 fewer identity), and changes mean MAE from 8.43 +/- 4.14 pts (filter off) to 7.38 +/- 2.38 pts (filter on) — an improvement in 4 of 5 genuinely-paired folds and lower variance, but still **not statistically significant** (Wilcoxon signed-rank, p=0.4375, n=5 folds — 5 paired folds is not enough power to confirm this). This is a real yield/quality trade-off (a small session-count cost for a directionally better, but not yet proven, MAE and variance reduction), not a free lunch. Re-run this ablation as the labeled dataset grows past the current ~10-identity bottleneck to get a properly powered read.

**Third review fix (2026-07-18):** `compute_session_confidence`'s per-session report set `n_below_threshold` to the full frame count for duplicate-`frame_name` sessions, even though those frames were never scored at all (NaN) rather than scored-and-found-low — summing that column across `symmetry_confidence_report.csv` would have silently double-counted the 42 duplicate-frame sessions against `main()`'s own top-level printout, which already keeps "below threshold" and "NaN" as separate buckets. Fixed to `0`; the real report was regenerated and `report_df['n_below_threshold'].sum()` now equals 154, matching the printed count exactly.

**Update, 2026-07-18 (Milestone 4 — Wrist-Speed-Guided Adaptive Sampling):** `zero_storage_pipeline.py`'s `extract_keypoints_in_memory` previously sampled the 7 canonical phases (stance...follow-through) at uniform time intervals across a detected shot window, assuming the swing progresses at constant speed. It doesn't: stance/trigger is a relatively static setup, while backlift-to-contact happens explosively fast, so uniform sampling risked landing "contact" on a transitional frame near — not at — the real moment of bat-ball contact. `find_wrist_speed_peak_frame` now does a coarse, bounded pre-scan (`WRIST_SPEED_COARSE_SAMPLES = 20`, a tunable starting point) of the shot window, tracking the max of left/right wrist landmark speed to locate the frame of peak wrist speed — a proxy for contact — reusing the module-level `detector` created once at import time (previously unused by the rest of the file, so this is a net reduction in duplication, not an addition). `redistribute_phase_indices` (pure, no video/MediaPipe dependency) then anchors the 7 phases on that peak: the 5 phases before contact are distributed linearly across `[start_frame, peak_frame]`, and contact/follow-through land at `peak_frame`/`end_frame` exactly. Same phase count, order, and labels as before — only *where* each phase is sampled changes. If no reliable peak is found (window too short, wrists not visible), `extract_keypoints_in_memory` falls back to the original uniform formula unchanged, logged via `log_rejection(..., "WRIST_SPEED_PEAK_NOT_FOUND", ...)`.

Verified mathematically, NOT against real video (a claim made at implementation time and retracted on review — see below). `redistribute_phase_indices` produces byte-identical indices to the old uniform formula when the peak happens to sit at the fraction (5/6 of the window) uniform sampling already assumed — proven as a unit test, not just asserted; that part of the verification stands.

**Review correction (2026-07-18, Principal Engineer pass):** the implementation-time summary claimed `find_wrist_speed_peak_frame`, run against the local `temp_ai_chunk.mp4`, correctly located a real stance-to-contact swing at 2.6s (full clip) / 2.32s (a hand-bounded 1.6s-3.2s sub-window), based on a handful of frames sampled at 0.4s intervals and a quick visual read of them. That read was wrong, caught by the user, not by further automated checking: `temp_ai_chunk.mp4` is a slow-paced nets session with long idle stretches between deliveries (the feeder walking to retrieve/reset the ball, the batsman adjusting gloves and walking back to the crease) — what was described as "stance at 2.0s, backlift at 2.4s, downswing/contact at 2.8s" was actually the recovery/reset period after a PREVIOUS delivery, not a live swing. Denser re-sampling (every 0.1s from 6.0s-9.4s) to find a cleanly identifiable stance-to-contact sequence for a corrected re-validation did not turn up one manual frame review could confidently label — the same "batsman standing at the crease while someone else handles the ball" pattern recurs repeatedly, and a real swing takes a fraction of a second, easily missed by human eyeballing of individual JPEG stills.

**What this does and doesn't mean:** `redistribute_phase_indices` (pure arithmetic) is proven correct by its unit tests, not affected by this. `find_wrist_speed_peak_frame`'s core claim — that peak wrist speed is a usable proxy for the moment of contact — remains mathematically sound as a hypothesis but is **not currently backed by real-video evidence**, because the "evidence" produced at implementation time was a misreading, and no valid replacement was found before this correction was written. `temp_ai_chunk.mp4` is also not a representative test case regardless: it's a full macro-trimmed nets clip with idle time and multiple deliveries, not the tight single-shot window (`ai_shots`, from NVIDIA's `find_shot_windows`) the real pipeline always passes in. The real, open risk this surfaces: if a shot window from `find_shot_windows` is loose (includes any pre-stance or post-followthrough buffer), a fast idle-time hand movement (ball pickup, glove adjustment) inside that buffer could register a higher wrist speed than the actual swing and get mistaken for contact — this is a genuine, undemonstrated-either-way limitation of the current design, not something this milestone's code defends against. No design change was made in response to this, since no validated fix is available yet and none should be invented under review pressure to look resolved — this is recorded as a known, open limitation for future validation against a session with confirmed frame-accurate ground truth, not fixed here. One real, proportionate fix WAS made: `extract_keypoints_in_memory` previously only logged the fallback case (`WRIST_SPEED_PEAK_NOT_FOUND`) — every session where a peak *was* found produced no record at all, which is part of why the false validation claim above went unchecked in the first place. It now also logs `WRIST_SPEED_PEAK_FOUND` with the peak's fraction of the window (0=start, 1=end) for every session, so real pipeline runs build a spot-checkable record (e.g. peaks clustering near 0 or 1 would be a red flag for idle-motion contamination) instead of leaving this entirely unobservable.

**Second review correction (2026-07-18) — confirmed defect, feature disabled by default:** asked to specifically re-verify whether the correct frames are being collected, a rigorous (not visual-guess) check was run: computed wrist speed at every single raw frame (not the coarse 20-sample scan) across a real window in `temp_ai_chunk.mp4` to get a ground-truth speed profile, confirmed the coarse algorithm lands within 3 frames of that true peak (frame 154 vs. frame 151 — the coarse-sampling mechanism itself is internally consistent), then overlaid the detected wrist/nose landmarks onto the actual frame at the peak to see who they belong to. **They belong to the feeder/coach walking toward the crease with the ball, not the batsman** — visually confirmed, not inferred (nose landmark lands on the feeder's face). MediaPipe's `PoseLandmarker` here runs with the default `num_poses=1`: it detects one person per frame with no guarantee it's the batsman, and in this real multi-person footage it locked onto the wrong one.

A candidate mitigation was tested before considering it, not shipped on theory: hypothesized that a real swing is wrist-dominant (wrist moves fast, hip/torso barely moves) while a person-tracking jump would move everything at once, so rejecting high-wrist/low-hip-speed-ratio spikes might not distinguish them. Measured the actual wrist-to-hip speed ratio at the confirmed false peak: **34.43** — wrist fast, hip essentially stationary. This is indistinguishable from what a real swing's signature would look like, because a person casually swinging one arm while walking normally produces the identical wrist-dominant, hip-stable pattern. This candidate fix was rejected based on real measurement, not shipped.

No validated fix exists. Rather than leave a confirmed-broken mechanism enabled with only a comment warning about it, `WRIST_SPEED_SAMPLING_ENABLED` was added (defaulting to `False`) and `extract_keypoints_in_memory` now always uses the original, previously-proven uniform sampling formula regardless of what `find_wrist_speed_peak_frame` would have found. `redistribute_phase_indices`, `find_wrist_speed_peak_frame`, and `_peak_speed_frame` are unchanged, still correct, and still covered by their unit tests (including a new regression test asserting the flag stays `False` until a validated fix lands) — only their use in the real pipeline is gated off. This milestone currently ships no behavior change to the real dataset-collection pipeline; it ships tested-but-not-yet-safe-to-use code and an honest account of why.

**Third review round (2026-07-18) — verified the disable fix works, then went further and characterized real frame-collection reliability broadly:** first, verified (not just re-asserted) that disabling the feature actually works: timed the gated call against real video (0.0s elapsed -- `find_wrist_speed_peak_frame` is provably never invoked when disabled) and confirmed the resulting indices are byte-identical to the pre-Milestone-4 uniform baseline; grepped the repo and found no other caller of these functions anywhere. This confirms Milestone 4's own defect is closed.

Asked to actually produce real collected frames as proof (not just index comparisons), two more things were found while trying, both broader-than-Milestone-4 but directly relevant to "can frame collection be trusted": (1) checked 3 more high-wrist-speed candidates in the same nets clip (`temp_ai_chunk.mp4`) besides the one already found -- all 3 also tracked the feeder, not the batsman, confirming this is the camera framing's systemic behavior for that clip, not a one-off; (2) switched to a different local video with genuine single-subject close framing (`WhatsApp Video 2026-07-02 at 1.31.36 AM.mp4`) to get a fair test, and found pose detection itself is only ~45% reliable at fine (0.1s) granularity in this real, low-light indoor footage -- likely motion blur plus small/distant subject -- to the point that the literal uniform-sampling formula, run on a real hand-bounded shot window, returned 0/7 successful detections. Of 7 hand-selected timestamps where detection DID succeed, 6 correctly landed on the batsman (verified by landmark overlay) and 1 was a false positive on an inanimate equipment bag in the foreground, not a person at all. Checked whether the existing `validate_pose()` topology check (ankle must sit below knee below hip for stance/trigger) would have caught that false positive: yes -- measured `avg_ankle.y=0.7700 < avg_knee.y=0.7717` on the real detection, which fails the check and would be rejected. This is a materially different, more benign failure mode than the feeder-tracking issue: a topologically-nonsensical false positive (random object) is already caught by pre-existing validation, while a topologically-normal wrong PERSON (a standing human, batsman or not) is not and can't be by that same check.

None of this is Milestone-4-specific code needing a fix -- `extract_features_from_image_array`/`validate_pose` are pre-existing, out of this milestone's file scope, and the disable already applied covers Milestone 4's own contribution. It's recorded here because it directly bears on the question actually being asked across this whole review thread ("does the pipeline collect correct frames") and because an honest answer needs both findings: a real, unguarded risk (wrong person, multi-subject footage) and a real, already-guarded one (non-human false positive, single-subject footage) look different and shouldn't be conflated.

**Fourth review round (2026-07-18) — ran the real, current production path end to end, definitive result:** to settle this properly, `find_shot_windows` (the actual NVIDIA API call `process_single_row` uses in production) was run for real against `temp_ai_chunk.mp4` (the actual production input file, not a hand-guessed window). It returned 3 real shots: `0.0-1.12s`, `3.32-6.68s`, `8.88-9.96s`. `extract_keypoints_in_memory`'s current, active logic (uniform sampling -- Milestone 4's feature is still disabled) was run on all 3 real windows: **all 3 got 7/7 pose detections** (unlike the hand-guessed WhatsApp-video window, which got 0/7) -- AI-detected windows are evidently tightly bound enough for reliable detection. But checking WHO was tracked, via landmark overlay, on frames from all 3 shots (stance, contact, and full-backlift phases checked specifically): **the feeder is tracked in every single one, not the batsman** -- confirmed across 5+ separate frames now, 100% consistent.

This means the wrong-person-tracking defect is not a Milestone-4-only, hand-picked-window artifact -- it reproduces exactly the same way through the real, current, always-was-there production path (`find_shot_windows` -> `extract_keypoints_in_memory` -> `extract_features_from_image_array`, all unmodified by Milestone 4) on the real production input file. For this specific real session, if it had been processed by the live pipeline right now, all 7 frames written to `keypoints.csv` would be the feeder's pose, not the batsman's -- and `validate_pose()`'s topology check would not catch it, since a standing feeder passes the same Y-ordering checks a standing batsman would.

**Fifth review round (2026-07-18) -- checked whether a DIFFERENT existing filter, further downstream, provides a safety net topology checking doesn't; found a genuinely mixed, real answer:** `kinematic_validator.py`'s bone-length coefficient-of-variation filter operates later in the pipeline (on `keypoints.csv` -> `keypoints_validated.csv`) and checks something different -- not "is this a plausible human topology" but "do this session's bone lengths stay consistent across its 7 frames." Hypothesized this wouldn't help either, on the theory that consistently tracking the SAME (wrong) person throughout a session would produce self-consistent, and therefore unflagged, bone lengths. Tested directly against all 3 real AI-detected shots from the round above, computing actual bone-length CVs from the real (feeder-tracked) landmark data: **2 of 3 real shots WOULD be caught and flagged invalid** by this filter (shot 2: `shoulder_span` CV=0.356, `hip_span` CV=0.407, both over the `MAX_BONE_CV=0.25` threshold; shot 3: `shoulder_span` CV=0.291) -- because the actively-moving feeder's apparent body proportions vary across frames as he walks/turns relative to the camera, which happens to trip bone-length consistency even though his actual skeleton isn't changing. **Shot 1, however, was NOT caught** -- no bone exceeded the threshold, so it would pass through unflagged with the wrong person's pose data.

**Update, 2026-07-18 (interview-deadline reprioritization) -- critical pre-existing bug found and fixed while rebuilding `dataset_angles.csv`:** `feature_engineering.py`'s `pad_group` reindexes each session's rows against a `canonical_frames` list to guarantee exactly 7 rows per session. That list was `'frame_01_stance.jpg'`-style (with a `frame_` prefix and `.jpg` suffix) -- but the CURRENT, active `zero_storage_pipeline.py` has for some time written bare `frame_name` values (`'01_stance'`, no prefix/suffix; see its `phase_labels` list). Real data has both conventions coexisting. For any session using the newer bare format, `reindex()` found zero matching index values, so `ffill`/`bfill` had nothing to pull from and **every column for that session -- not just `frame_name`, but `score_balance`, `bowling_type`, all of it -- came out as `NaN`**. Verified against real data before fixing: **83 of 197 sessions (42%) in `dataset_angles.csv` had `NaN` scores**, silently present in the file, invisible unless specifically checked (a NaN score would either crash training or, if unguarded, corrupt loss computation). `ablation_stance_symmetry_filter.py` (Milestone 3) had copied the same stale `CANONICAL_FRAMES` list and carried the identical bug.

Fixed by adding `normalize_frame_name()` to `feature_engineering.py` (strips an optional `frame_` prefix and `.jpg`/`.jpeg`/`.png` suffix before matching), applied in both files' `pad_group` before the reindex, with `canonical_frames`/`CANONICAL_FRAMES` updated to the bare format; `ablation_stance_symmetry_filter.py` now imports the shared function rather than re-defining its own copy. Covered by 4 new tests in `test_feature_engineering.py`, including a regression test proving both real conventions now normalize to the same value. Re-ran the real pipeline after the fix: `dataset_angles.csv` regenerated with **0 NaN scores across all 197 sessions**, and the complete-7-frame trainable pool grew from ~120 sequences / ~10 identities (the number Milestone 3's ablation was run against) to **197 sequences / 44 identities** -- this bug had been silently discarding close to half of the already-collected, already-labeled real dataset. All model retraining and evaluation numbers from here forward use the corrected pipeline; anything cited from before this fix (including Milestone 3's ablation MAE numbers) was computed on the smaller, bug-affected pool and is superseded, not comparable.

This is a real, meaningful, but partial and accidental mitigation, not a designed defense -- it depends entirely on how much the wrongly-tracked person happens to move during that specific window, which is not something the pipeline controls or checks for directly. It should not be treated as reliable coverage, but the earlier framing ("nothing in the current pipeline would catch or flag this") was incomplete and is corrected here: something does catch it, sometimes, as a side effect of an unrelated check.

**Still not a Milestone-4 fix, and flagged as a separate follow-up, not silently patched here:** the affected code (`extract_features_from_image_array`, `validate_pose`) is pre-existing and out of this milestone's scope ("do not modify unrelated modules"); a real fix (multi-person detection + a subject-selection heuristic, or a source of footage guaranteed single-subject) needs its own scoped, validated milestone, not a rushed change appended to this one. What's unknown and worth stating plainly: how much of the *already-collected* real `keypoints.csv` data is affected is not established here -- this was checked against one specific nets-session-style clip with a visible feeder, not the full dataset, and other footage (e.g. single-camera clips without a prominent second person) would not necessarily have this problem.

`openai==2.44.0` (already pinned in `requirements.txt` but not installed in this environment) was installed to make `zero_storage_pipeline.py` importable at all for testing — a pre-existing environment gap, not a code change.

**Update, 2026-07-20 (Milestone 4 — multi-person subject selection, audit C1):** the wrong-person-tracking defect documented across the review rounds above now has a shipped, enabled mitigation. `extract_features_from_image_array` runs MediaPipe with `num_poses=4` (was the default 1), collects EVERY candidate person per frame, and makes one session-level subject decision in the new `dataset/subject_selection.py`: candidates are associated into tracks by hip-center proximity (gated in torso lengths, widening across detection gaps), a track must cover ≥4 of 7 frames to qualify (deliberately equal to `apply_pipeline_rules`' survival rule), and with multiple qualified tracks the winner must have BOTH maximal coverage AND ≥1.25× the mean torso size of every rival — otherwise the session is **rejected** (`SUBJECT_SELECTION_REJECTED` in the rejection log) rather than scored on a guess. Every multi-track decision is positively logged (`SUBJECT_SELECTED`) — the absence of exactly this kind of record is how the original defect stayed invisible. Because Milestone 3 routed Django serving through this same function, one change point covers ingestion and the product.

What was actually measured (not assumed), on the real `frames/Sai_front_1` session: (1) single-person equivalence — `num_poses=4` returns exactly one candidate in 7/7 real frames, landmarks within 0.01 of the `num_poses=1` detection, and the full pipeline passes the session end-to-end; (2) real two-person scenes, built from person-cropped composites after discovering MediaPipe simply cannot detect a person below a size threshold (a 55% copy beside the FULL frame was never detected — itself a documented empirical finding): at tile scale 0.75 both figures are detected (2 candidates in 5/7 frames) and the larger is selected in every frame across repeated runs; at scale 1.0 (equal sizes, 2 candidates in 7/7 frames) selection refuses to guess, as designed; (3) latency — 169.3 → 172.3 ms/frame (+1.8%) for `num_poses` 1→4 on this machine.

**Still open, stated plainly:** the heuristic is validated against synthetic scenes and real-imagery composites, NOT against a real multi-person video with frame-accurate ground truth (none exists in the repo — the original failure clip `temp_ai_chunk.mp4` was deleted by the zero-storage design). The adversarial documented case (feeder detected in all frames while the batsman blurs out at contact) now REJECTS instead of silently scoring the feeder — correct per the rejection-over-wrong-scoring principle, but it recovers no session. The dominance thresholds (coverage ≥4, size ≥1.25×) are documented starting points in the `MAX_BONE_CV` tradition. The historical `keypoints.csv` has NOT been audited for already-ingested wrong-person sessions — that measurement (and any cleanup) remains a separate, human-reviewed step.

## Explicit Layer Details

1. **Input Layer:** `(None, 7, 30)` - 7 frames, 30 features (15 angles + 15 velocities)
2. **Conv1D:** `(None, 7, 64)` - 64 filters, `kernel_size=3`
3. **BatchNormalization & Dropout (0.2)**
4. **Bidirectional(LSTM):** `(None, 7, 128)` - 64 units per direction
5. **Dropout (0.3)**
6. **TemporalAttention:** `(None, 128)` - Custom attention layer
7. **Dense:** `(None, 32)` - Intermediate regression head
8. **Dense:** `(None, 4)` - Final sigmoid output (Balance, Power, Technique, Defence)
