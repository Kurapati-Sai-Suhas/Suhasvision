1. Introduction
1.1 Purpose
This document defines the complete software requirements for the Cricket Batting Stance Analyzer — a full-stack AI-powered web application that evaluates a cricketer's batting stance using two data sources: a self-reported stance form and real video frame analysis via the Claude Vision API.
This SRS is intended as the single source of truth for design, development, and testing decisions throughout the project lifecycle.
1.2 Project overview
The system accepts up to 3 batting videos from the user, extracts 10 key frames per video using ffmpeg.wasm in-browser, and sends those frames alongside form parameters (grip, backlift, foot position, head alignment, weight distribution, etc.) to Claude's multimodal AI for a unified stance report. The report includes an overall score, per-dimension scores, visual insights from video, strengths, weaknesses, and drill recommendations.
1.3 Scope
In scope
Web-based React frontend with multi-step stance form
In-browser video frame extraction using ffmpeg.wasm
Claude Vision API integration for stance analysis
FastAPI backend for API key security and request proxying
Optional: custom deep learning pose model using MobileNet/VGG16 (Phase 2)
Scoring system across 6 dimensions: balance, power, technique, defence, attack, footwork
Drill and improvement recommendation engine
Out of scope (for now)
Mobile native app (iOS/Android)
Real-time video streaming / live camera analysis
Multi-player comparison dashboards
Coach login / student management portal
Commercial billing / subscription management

2.2 Data flow
User fills in stance form (Step 1 & 2 of UI)
User uploads up to 3 batting videos (Step 3)
ffmpeg.wasm extracts 10 frames per video in-browser (no server needed for this step)
Frontend sends form data + base64-encoded frames to FastAPI backend
Backend validates payload, appends Claude API key, forwards to Anthropic API
Claude Vision model reads all frames + form data, returns JSON analysis
Frontend renders the full stance report with scores, video insights, drills

4. Functional requirements
4.1 Frontend requirements
FR-01: Multi-step stance form
The UI shall present a 4-step wizard: Profile → Stance parameters → Video upload → Analysis
All form state shall persist across steps without data loss
Each step shall validate completeness before advancing
FR-02: Stance parameter capture
System shall capture: batting hand, playing level, preferred style
System shall capture: foot position, stance width, guard, head position, knee bend, weight distribution, shoulder alignment
System shall capture: grip type, backlift direction, bat position at rest
System shall support multi-select for known trouble areas (short-pitch, spin, swing, etc.)
FR-03: Video upload and frame extraction
System shall accept up to 3 video files per session
Accepted formats: MP4, WebM, MOV — max 150MB per file
ffmpeg.wasm shall extract exactly 10 frames per video, evenly spaced across the full duration
Frame thumbnails shall be displayed to the user before analysis is triggered
Frame extraction shall occur entirely in-browser — no video data shall be sent to the backend
FR-04: AI analysis
System shall send all extracted frames (base64 JPEG) + form data to the backend in a single request
Backend shall forward this to Claude Vision API with a structured cricket coaching prompt
The response shall include: overallScore (0-100), playerType label, per-dimension scores, videoInsights, strengths list, weaknesses list, improvements list, and a coach note
Analysis shall work even when no videos are uploaded (form-only mode)
FR-05: Results display
Overall score and player type shall be prominently displayed
Six dimension scores (balance, power, technique, defence, attack, footwork) shall render as metric cards with colour-coded bars
Video insights section shall only appear when videos were provided
Drills and improvements shall be numbered and actionable
User shall be able to re-analyze with the same data after viewing results
4.2 Backend requirements
FR-06: API proxy
FastAPI backend shall expose a POST /analyze endpoint
The endpoint shall accept: stanceData (JSON object), frames (array of base64 strings), videoCount (integer)
The Claude API key shall never be exposed to the frontend — stored as an environment variable server-side
Backend shall validate payload size (max 20MB total) before forwarding to Claude
FR-07: Error handling
If Claude API returns an error, backend shall return a structured error response with a human-readable message
Frame extraction failures shall be gracefully handled — analysis proceeds with available frames
Oversized video files shall be rejected with a clear message before upload attempt
5. Non-functional requirements
5.1 Performance
ffmpeg.wasm initial load: < 8 seconds on a standard broadband connection
Frame extraction for a 2-minute video: < 15 seconds after ffmpeg is loaded
Claude API response time: typically 5–15 seconds depending on frame count
Frontend shall show progress indicators during all async operations
5.2 Security
Claude API key stored only in backend environment variables — never in frontend code or localStorage
All backend-Claude communication over HTTPS
No user video data stored server-side — frames are processed in memory and discarded after the API call
CORS policy on FastAPI backend restricted to the frontend's domain in production
5.3 Usability
The application shall be usable without any cricket coaching knowledge to navigate the UI
All stance option buttons shall use plain English labels (no jargon without explanation)
Frame thumbnail preview shall give users confidence their video was processed correctly
Mobile-responsive layout (min width 375px)
5.4 Maintainability
Frontend code organised in feature folders: /form, /video, /results, /api
All Claude prompts stored in a dedicated prompts.js file for easy tuning
FastAPI routes documented via auto-generated Swagger UI at /docs

6.1 The most important thing to build first
Start here — in this exact order

Step 2: Build the React form (Step 1 only — just Profile) and make sure state works
Step 3: Wire the form to a hardcoded fetch() call to Claude API (no backend yet)
Step 4: Display the raw JSON response on screen — you now have a working prototype!
Step 5: Add the backend to hide your API key — move the fetch() call server-side
Step 6: Add video upload + ffmpeg.wasm frame extraction
Step 7: Add frames to the Claude request and display video insights in results
6.2 The deep learning path (Phase 5 onwards)
This is where your Udemy course becomes the star. Here's exactly how to connect what you learned:
Your DL course → this project
Transfer learning + MobileNet → Use MobileNetV2 as backbone, freeze all layers, add GlobalAveragePooling2D + Dense(256, relu) + Dense(6, sigmoid) to predict 6 stance dimension scores simultaneously
VGG16 → Use as an alternative heavier backbone when you have more training data (200+ samples per class)
CNN architecture → Understand what MobileNet is doing under the hood when you fine-tune it
Data augmentation (ImageDataGenerator) → Flip, rotate, zoom batting images to grow your dataset
LSTM → Future: pass a sequence of frame feature vectors through an LSTM to model the swing motion over time
Model saving → model.save('stance_model.h5') → load in FastAPI → serve predictions
Activation functions → ReLU throughout hidden layers, Sigmoid on the 6 output neurons (each score is 0-1)

Skip raw image classification — extract 33 joint coordinates per frame and train a lightweight classifier on those vectors instead. Far fewer data points needed.

Pro tip: The MediaPipe + custom classifier route is the fastest path to a real ML model. Instead of classifying raw images (which needs thousands of samples), you use MediaPipe to extract 33 joint coordinates per frame, then train a small Dense network on those coordinates. You only need ~200–300 labelled examples to get decent accuracy.
